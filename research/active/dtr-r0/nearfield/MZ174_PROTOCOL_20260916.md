# MZ174: cross-return relations before another obstacle-readout fit

EXPLORE, consumed original TRAIN, 2026-09-16. The broad objective remains better
obstacle awareness with RGB + 8x8 dual-return ToF + Radar + IMU. MZ129 remains
the baseline/default; this first check is a sensor-relation component experiment.

## Question and changed mechanism

Can neighboring returns help distinguish returned ToF witnesses inside versus
outside the walking corridor across scenes? MZ171's raw return MLP processes
each 21-value slot independently; MZ172 adds its own zone's visual context.
Here each receiver exchanges messages with eight other valid returns. The
matched control retains the receiver, edges, masks, inputs and parameter count
but permutes sender content against the chosen edge. Both models are trained
from scratch. This tests useful correspondence between edge geometry and sender
content, not whether a larger pointwise head fits better.

The [RadarGNN source](https://github.com/TUMFTM/RadarGNN) and
[SpaRC paper](https://arxiv.org/abs/2411.19860v1) motivate relational processing
of sparse measurements. Their automotive point clouds, tasks and reported
numbers do not establish performance for these regional ToF observations.
No official model, code, weights or dataset is ported in this experiment.

## Public graph and matched learning

Use the authenticated MZ161 public token cache: 128 ToF slots and four Radar
slots, each with 21 public values and a validity mask. Each node retains its
own values. Eight nearest valid nominal body-center proxies supply messages;
self edges are excluded. Stable slot order resolves distance ties. Actual
relative center, relative range and same-modality descriptors stay attached to
each selected edge. The shuffled control applies a fixed label-independent
permutation of valid sender content; it can substitute the receiver's content
on an edge. Invalid nodes cannot send, receive a positive output, or enter loss.

Nominal centers are hypotheses, not actual ToF hit positions. Radar's zero-height
placeholder does not measure elevation. No center assumption narrows a return,
changes MERGED status, removes raw support or clips RGB-external observations.
All nodes may exchange information across modalities, but Radar labels remain
UNKNOWN and only ToF outputs are supervised or used by the optional readout.
RGB pixels/context are not inputs to this component screen. This is not a
complete four-sensor replacement or an absent-return recovery claim.

Architecture: 21-to-32 stem; one 69-to-32-to-32 message MLP; masked mean over
eight neighbors; 64-to-32-to-1 output MLP and an explicit 21-to-1 receiver skip.
ReLU activations are used in the stem and hidden MLP layers. The final logit
cutoff is zero in both arms. There is no threshold selection or confidence
claim. Nonalerts and unavailable labels remain UNKNOWN, not clear space.

Reuse only the MZ171 FIT144 known-return targets, bound to original TRAIN scene
groups 0, 1 and 2 in all four families. Three folds hold out one whole scene
group each (48 validation frames, 96 fitting frames). No frame in a fold is
trained using its own label. Scene identifiers control folds only, never model
input. Original scene3 HELD48 and original dev/test labels are not accessed in
this first stage; public cache presence does not authorize label use.

Each arm/fold uses seed 174016 + fold, identical initial parameters and orders,
AdamW learning rate .001, weight decay .0001, batch 16, and 120 epochs. Use the
last checkpoint, never the best intermediate result. Known positive and known
negative slots receive equal total loss mass over that fold's fitting records;
UNKNOWN receives zero. This differs from MZ171's per-frame balancing and joint
pixel/frame losses identically in both new arms. The controlled effect is the
edge/content relationship, not a claim that this one change explains MZ171.

## Decision and remaining delivery

Seal the protocol, code, data identities and orders before fitting, then seal
all out-of-fold slot logits/checkpoints before reducing validation metrics.
Report known TP/FP/FN/TN, recall, specificity, balanced accuracy, every scene
fold and family, unknown-positive counts and eligible-return coverage. Slots
within a frame are correlated and are not independent scenes.

Continue only if natural out-of-fold recall, specificity and balanced accuracy
are each at least 75%; balanced accuracy beats shuffled by at least five
percentage points; and no fold loses recall or specificity versus shuffled.
This is a fit-stage mechanism gate, not an obstacle-effect claim. If it fails,
close this fixed graph/neighborhood/schedule/control without tuning, adding
edges/layers, changing loss/cutoff or acquiring more data. Keep MZ129.

If it passes, fit both arms once on all FIT144 with the same final schedule and
evaluate the previously excluded original scene3 HELD48. Any final warning
diagnostic must retain the complete existing MZ129 Radar branch/guards from
the outset, ORed with the learned valid-ToF maximum. Fewer false warnings is
useful only with old true-frame/event timing and native warning retention;
report the sensor-only readout's unmeasured-surface limitation. No App/default
promotion or fresh claim follows this consumed check.

One 1,200-second allocation for the three-fold paired check; the conditional
full-fit/HELD stage has a separate maximum 600 seconds. Synthetic graph tests,
CPU/CUDA output/gradient parity and a measured equivalent forward/backward
placement check precede scientific fitting. Use float32 without autocast/TF32.
Retain failed mechanical attempts, sources, checkpoints and audit logs; release
task-owned processes at completion. No active paid or capture resources.
